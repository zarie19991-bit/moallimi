# اختبارات محلية لمحرك OMR الحالي

هذه اختبارات **للمحرك المرفوع من Supabase** وليست تنفيذًا بديلًا له.

## التشغيل

يلزم Bun، وNode/npm لتثبيت التبعية، و`unzip`.
التبعية الوحيدة للاختبار هي `jpeg-js@0.4.4`، وهي نفس نسخة مفكك JPEG في المحرك المنشور.

```sh
npm ci
npm run test:omr
bun qa/omr/diagnostics.ts
npm run compare:omr
```

في Replit، استخدم مسار إدارة الحزم المعتاد عند الحاجة إلى تثبيت التبعية.

## حدود العزل

- المصدر هو أرشيف المستخدم المحدد في `source-manifest.json`، مع التحقق من SHA-256 وأسماء الملفات.
- لا يستبدل الاختبار أي ملف في `supabase/functions/nafes-exam`.
- تُقرأ الملفات السبعة إلى مجلد مؤقت، وتُفحص التبعيات النسبية، ثم تُجمّع وحدتا OMR ومراجعة المسح لتعمل محليًا.
- لا يجري استيراد `index.ts`، ولا تشغيل `Deno.serve`، ولا إنشاء عميل Supabase.
- أي محاولة لاستعمال `fetch` وقت تشغيل الاختبارات ترفع خطأ.
- عمليات قاعدة البيانات تتجه إلى كائن في الذاكرة فقط؛ لا تُقرأ مفاتيح أو متغيرات Supabase.
- الصور مولّدة محليًا وفق هندسة المحرك، والأسماء والمعرّفات وهمية.
- `diagnostics.ts` يطبع إثباتات إعادة الإنتاج دون بيانات حقيقية.

هذا عزل على مستوى برنامج الاختبار، وليس حاوية أو جدارًا شبكيًا على مستوى نظام التشغيل.

## نتيجة الأساس الأصلية قبل أي إصلاح

تشغيل 27 اختبارًا على المصدر الأصلي: **22 نجحت، 5 فشلت**.
كان تشغيل الأساس الأصلي يعيد exit code 1 لأن الحالات الخمس لم تُصلح حينها.
التشغيل الحالي يستهدف نسخة الإصلاح للحالات الخمس، كما هو موضح أدناه.

الحالات الفاشلة في `regressions.test.ts`:

1. فقاعتان مظللتان بلونين مختلفين: سوداء وزرقاء، تُقرأان كإجابة زرقاء واحدة واضحة.
2. صورة ورقة صحيحة مدوّرة 90 درجة تفشل في اكتشاف علامات المحاذاة.
3. صورة ورقة صحيحة مدوّرة 180 درجة تفشل في اكتشاف علامات المحاذاة.
4. `teacher_scan_list` يغيّر لقطة مراجعة يدوية قديمة بدل الاقتصار على عرضها.
5. `teacher_scan_alerts` يفعل ذلك أيضًا.

الاختبارات الخمسة نفسها الآن تستهدف نسخة التطوير بعد إصلاحها، دون تخفيف توقعاتها.
التفاصيل والأسباب الأصلية في `docs/omr-deployed-source-audit.md`.

## نسخة التطوير والنتيجة الحالية

- `development/source` نسخة منفصلة من الملفات السبعة المرفوعة.
- التغييرات في `omr-server.ts` و`paper-scan.ts` فقط، وليس ملفات التطبيق أو مصدر ZIP الأصلي.
- `npm run test:omr`: **57 ناجحة، صفر فاشلة**؛ الاختبارات الأساسية تعمل على الأصل وعلى التطوير.
- `npm run compare:omr`: مقارنة 11 صورة مصطنعة / 660 إجابة.
- قبل: 459 متطابقة، 21 مختلفة بعد القراءة، 180 تعذر قراءتها.
- بعد: 660 متطابقة، صفر مختلفة، صفر غير مقروءة.
- `results/comparison.json` و`results/comparison.html` يتضمنان النتائج وصور المقارنة والإجابات.
- `diagnostics.ts` يعرض السلوك الأصلي لتوثيق المشكلة، وليس سلوك نسخة التطوير.
- التقرير بعد الإصلاح في `docs/omr-local-fix-results.md`.

لإضافة أوراق فعلية **محلية** مجهولة الهوية، جهز ملف JSON بهذا الشكل،
ثم شغّل `bun qa/omr/comparison.ts --manifest path/to/manifest.json`.
المسارات تحسب بالنسبة إلى ملف JSON. يجب تعليم الإجابات المظللة فعليًا،
وليس نسخ مفتاح إجابات الاختبار:

```json
[
  {
    "id": "old-sheet-synthetic-student",
    "image": "old-sheet.jpg",
    "expected": [
      {"question": 1, "status": "clear", "selected": 1},
      {"question": 2, "status": "blank", "selected": null},
      {"question": 3, "status": "multiple", "selected": null, "marked": [0, 2]}
    ]
  }
]
```

الخيارات مرقمة من صفر إلى ثلاثة، حسب ترتيب الفقاعات في القالب.
التقرير يفصل صور المستخدم عن الصور المصطنعة. وجود عينات قليلة لا يثبت تغطية كل النماذج.

## قبل اعتبار دقة OMR مثبتة

هذه الصور المصطنعة لا تثبت دقة المحرك على أوراق المدرسة.
يلزم لاحقًا توفير نموذج الورقة الفعلي وعينات مجهولة الهوية مع مفتاح إجابة مستقل.
يجب تغطية الأقلام المختلفة، التظليل الخفيف، المحو، الإجابات المتعددة والفارغة،
الدوران والميل والمنظور والظلال والدقة المختلفة.

قارن لكل سؤال: الخيار أو الخيارات المتوقعة، وحالة القراءة، والحاجة للمراجعة اليدوية.
قِس الإجابات الخاطئة التي يصنفها المحرك «واضحة» منفصلة عن الحالات التي يرفضها أو يطلب مراجعتها.
لا تُشغّل اختبار اعتماد درجات حقيقي قبل توفير نسخة QA مصرّح بها ومخططها، ولا تُنشئ قاعدة جديدة تلقائيًا.

## اختبار الأوراق الست الحقيقية

ملف المستخدم المجهول الهوية يحتوي ست صفحات. لم يُرفق مفتاح للتظليل الفعلي.
فُرّغت الخيارات بصريًا من الصور أولًا، ثم قورنت بالمحركين. أُعيد فحص أربع فروق
بصور مكبرة، وتبين أنها أخطاء في التفريغ اليدوي. سجل التصحيحات محفوظ وليس مخفيًا.
المراجع البصري مساعد واحد؛ المرجع غير مؤكد بصورة مستقلة من المستخدم.

```sh
python3 .agents/scripts/render_omr_samples.py
python3 .agents/scripts/inspect_omr_regions.py
bun qa/omr/real-six.ts
python3 .agents/scripts/report_real_omr.py
npm run test:omr
```

- أدوات Python تحتاج `pymupdf` الموثق في `pyproject.toml`؛ لا تنشئ منصة أو قاعدة جديدة.
- `results/real-six/report.html`: الصور، مواقع القياس، والخيارات الستون لكل ورقة.
- `answers.csv`: 360 صفًا للخيارات قبل وبعد والمراجعة البصرية.
- `visual-comparison.json`: المقارنة وحدود المرجع وسجل مراجعات التفريغ.
- `alignment-evidence.pdf`: نسخة دليل منفصلة مع علامات مواضع القياس؛ الأصل لم يُعدّل.
- الأصل والتطوير: **360 متطابقة، صفر اختلاف، صفر غير مقروءة** لكل نسخة.
- لا يوجد تحسن قابل للقياس في هذه العينات؛ الأصل كان مطابقًا أيضًا.
- لا توجد حالة فعلية متعددة أو فارغة أو غير محسومة في المجموعة؛ لا تدّعي تغطيتها.
- اختبارات `real-six.test.ts` تتخطى العينات إذا غابت صورها المحلية، ولا تعلن نجاحًا وهميًا.
- التشغيل بعد إضافة العينات الست كان **72 اختبارًا ناجحًا، صفر فاشل**.
  مهلة كل اختبار 60 ثانية لاستيعاب فك الصور بالحجم الفعلي وفحص الاتجاهات
  عند بطء التنفيذ؛ هذه ليست هدف أداء إنتاجيًا، ولا تغير معايير صحة الخيارات.

## إصلاح لون الورق والحبر الثاني الضعيف

أضيف قياس لون الورق المحيط بكل فقاعة قبل قياس الأزرق. لا يفترض المحرك
أن ورق الصورة أبيض محايد؛ الإضاءة الزرقاء لا تصبح تظليلًا متعددًا.
الحبر الثاني الضعيف المتفق عليه بين قياس المركز والحلقة يحال للمراجعة
إذا لم يكف لتصنيف متعدد موثوق، ولا يعتمد الخيار الأزرق تلقائيًا.

```sh
bun qa/omr/hardening-probe.ts probe-after.json
python3 .agents/scripts/report_omr_hardening.py
npm run test:omr
```

- التشغيل النهائي: **79 ناجحة، صفر فاشلة**.
- `results/hardening/report.html`: تقرير جامع يفصل العينات الأصلية والمعدلة والمصطنعة.
- ثلاث صفحات أصلية استُخدمت لإنشاء صور تحكم وإضاءة معدلة: 360 اختيارًا؛
  الأصل 180 متطابقة، والتطوير السابق 240، والتطوير الحالي 360.
- هذه الصور ليست أوراقًا فعلية إضافية ولا إثباتًا لقالب قديم.
- أربع حالات مصطنعة لتظليل مختلط: الأصل يعتمد الأربع كخيار واحد؛
  التطوير الحالي يصنف ثلاثًا متعددة ويحيل واحدة غير محسومة للمراجعة.
  الأخيرة ليست تطابقًا تامًا مع تصنيف متعدد المتوقع، ولا تُخفى من المقارنة.
- `probe-before.json` سجل تاريخي محمي من الاستبدال العرضي.

## اللقطات التاريخية وحالة عدم الحسم

أكد المستخدم أن ملف الأوراق الست هو المجموعة القديمة المقصودة. نتائج إعادة القراءة
الحالية لا تمثل تلقائيًا نتائج المسح المخزنة في Supabase.
استعمل `export/historical-snapshots-readonly.sql` للحصول على نسخ مجهولة من
`snapshot` و`effective_snapshot` عبر SELECT فقط، دون استدعاء مسارات Edge التي قد تعيد المعالجة.
لا توجد صلاحية Supabase معتمدة حاليًا، ولم يُنفذ الاستعلام على الإنتاج.

إصلاح إضافي في نسخة التطوير يحفظ `ambiguous` ذات المرشحين كـ`uncertain` لا `multiple`.
اختبارات التسجيل على الذاكرة تحفظ المراجعة المطلوبة ولا تكتب محاولات الطلاب.
**التشغيل الحالي: 81 ناجحة، صفر فاشلة.**
التفاصيل في `docs/omr-historical-baseline.md`.

## الانحدار الاصطناعي الحالي للتصنيف

```sh
npm run test:omr:classification
```

**94 ناجحة، صفر فاشلة** في خمسة ملفات اصطناعية فقط. لا تستخدم الأوراق القديمة أو درجاتها.
رقم 81 أعلاه سجل التشغيل الشامل السابق، قبل توسيع منطق الفصل بين القراءة والهوية والمفتاح.
التقرير: `results/classification/report.html`، والبيانات والبصمات: `evidence.json`.
التفاصيل: `docs/omr-classification-repair.md`.

وجود مرشحين لا يثبت التعدد، وعلامة `verified` وحدها لا تسمح باعتماد قراءة غير محسومة.
`selected` لا يحمل مرشحًا كإجابة مؤكدة؛ `reader_selected` يحتفظ به لأغراض التشخيص فقط.
