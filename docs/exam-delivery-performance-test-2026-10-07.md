# مستند اختبار أداء واعتمادية تسليم الاختبارات

**التاريخ:** 7 أكتوبر 2026  
**المنصة:** معلّمي — نافس

## 1. الهدف

التحقق من أن تحسينات التسليم تقلل فقد الإجابات وتحوّل أعطال الشبكة المؤقتة من “فشل تسليم” إلى “تأخير مزامنة قابل للاسترداد”، مع عدم إنشاء تسليمات مكررة.

## 2. القياس قبل التعديل — إنتاج حقيقي

من سجلات Supabase Edge لمسار `nafes-exam` في نافذة القياس المتاحة:

| الحالة | العدد | المتوسط | P95 |
|---|---:|---:|---:|
| HTTP 200 | 15,004 | 664.7ms | 1,186ms |
| HTTP 409 | 206 | 1,008.4ms | 1,799.5ms |
| HTTP 404 | 56 | 444.7ms | 608ms |
| HTTP 403 | 28 | 715.3ms | 1,370.8ms |
| HTTP 400 | 2 | 2,607.5ms | 3,106.5ms |
| HTTP 520 | 2 | 17,461.5ms | 24,598.9ms |

ملاحظات:
- 520 نادر عدديًا لكنه شديد البطء.
- 409 ليس مؤشرًا مباشرًا على فشل التسليم؛ السجلات تضم أقفال جلسة وتعارضات عمليات إدارية.
- وجدت حالات محدودة لقفل محاولة في جهاز/تبويب آخر.
- ثبت وجود خلل منطقي مستقل في المسار القديم: إعادة `finish` بعد نجاح سابق كانت تُرجع 409 بدل نجاح Idempotent.

## 3. القياس الأولي بعد نشر Backend

بعد وصول `nafes-exam` إلى v105، وُجد في السجلات:

| الحالة | العدد المرصود | المتوسط | P95 |
|---|---:|---:|---:|
| 200 | 564 | 885ms | 1,355.4ms |
| 409 | 32 | 870.7ms | 1,243.2ms |
| 403 | 4 | 387.5ms | 423.6ms |

هذه **عينة أولية** وليست مقارنة نهائية سببية؛ حجمها أقل من القياس التاريخي، كما أن الواجهة الجديدة تحتاج نافذة تشغيل أطول بعد نشر GitHub Pages. عدم ظهور 5xx/520 في هذه العينة إيجابي لكنه لا يكفي وحده لإثبات المعدل طويل الأجل.

## 4. محاكاة فوضى Algorithmic Chaos

تم إنشاء الاختبار:
`question-bank/scripts/simulate-delivery-chaos.mjs`

المحاكاة لا ترسل آلاف الطلبات إلى الإنتاج؛ بل تختبر منطق الحفظ المحلي، retries، فقد الاستجابة بعد commit، وIdempotent finish داخل CI.

### إعداد المحاكاة

- 5,000 طالب افتراضي.
- 15 سؤالًا لكل طالب.
- 18% من الطلاب يمرون بفترة Offline أثناء الإجابة.
- معدل فشل نقل افتراضي:
  - 12% للحفظ.
  - 16% للتسليم.
- بعض الفشل يحاكي HTTP 520.
- 3% من عمليات التسليم الناجحة على الخادم تُحاكى كـ “Commit نجح لكن استجابة HTTP ضاعت”.
- حتى 5 retries للدورة، ثم دورات استرداد إضافية لنية التسليم.

### النتيجة

| المؤشر | النتيجة |
|---|---:|
| الطلاب الافتراضيون | 5,000 |
| الأسئلة لكل طالب | 15 |
| طلاب مروا بفترة Offline | 928 |
| طلبات النقل المحاكاة | 32,348 |
| حالات فشل عابرة | 4,052 |
| محاولات Retry | 4,204 |
| Commit ناجح مع استجابة مفقودة | 153 |
| إيصالات تسليم | 5,000 |
| إجابات مفقودة بعد الاسترداد | **0** |
| تسليمات نهائية مكررة | **0** |
| نسبة الوصول إلى إيصال | **100% في المحاكاة** |

هذه نتيجة لاختبار منطق الاعتمادية، وليست SLA إنتاجية ولا تعني أن شبكة المدرسة ستضمن 100%.

## 5. سيناريوهات الاختبار المعتمدة

### S1 — تشغيل طبيعي
- الطالب يجيب 15 سؤالًا.
- Auto-save بعد التغيير ودوريًا.
- المتوقع: الحفظ يصل للخادم ويظهر إيصال عند التسليم.

### S2 — انقطاع 60–90 ثانية
- قطع الشبكة أثناء منتصف الاختبار.
- الطالب يواصل الإجابة.
- المتوقع: الإجابات تبقى في Local Draft، ثم تتم مزامنتها بعد عودة Online.

### S3 — Gateway 503/520 أثناء الحفظ
- حقن استجابة مؤقتة.
- المتوقع: Retry مع Backoff/Jitter؛ عدم حذف النسخة المحلية.

### S4 — فقد استجابة التسليم بعد نجاح Commit
- الخادم يحفظ التسليم، لكن العميل لا يستلم HTTP response.
- المتوقع: إعادة `finish` ترجع نجاحًا وإيصالًا، ولا ينشأ Record ثانٍ.

### S5 — انقطاع قرب نهاية الوقت
- آخر إجابات تبقى محليًا.
- الاتصال يعود خلال Recovery Grace.
- المتوقع: `assessment_finish` يدمج الإجابات المحلية الموثقة في نفس المحاولة خلال دقيقتين من انتهاء الوقت.

### S6 — انقطاع أطول من Recovery Grace
- المتوقع: الخادم يعتمد آخر إجابات سبق أن استلمها؛ لا يسمح بتمديد غير محدود.

### S7 — Refresh/إغلاق ثم إعادة الفتح
- المتوقع: استعادة نفس attempt وإجابات Local Draft إذا كانت لنفس attempt_id ولم تتجاوز TTL.

### S8 — ضغط متزامن على بيئة Staging
يوصى بتنفيذ HTTP Load Test على نسخة Staging، وليس المشروع الحي، بالدرجات التالية:
- 100 طالب متزامن — 10 دقائق.
- 500 طالب متزامن — 10 دقائق.
- 1,000 طالب متزامن — Burst لمدة دقيقتين ثم Steady لمدة 8 دقائق.
- إن كانت المؤسسة تستهدف آلافًا متزامنة، يزاد الحمل تدريجيًا ولا يقفز مباشرة إلى الرقم الأقصى.

## 6. معايير القبول

| المعيار | القبول |
|---|---|
| فقد الإجابات في Chaos Test | 0 |
| Duplicate final records | 0 |
| إيصال بعد تعافي الاتصال | 100% في المحاكاة |
| p95 للحفظ في التشغيل المعتاد | < 2 ثانية مستهدف |
| 5xx/52x | < 0.5% في نافذة 10 دقائق |
| Pending final submissions | لا تبقى معلقة بعد عودة الاتصال الطبيعية |
| Local durable cache | لا يحتوي PII أو access token |
| Retry storm | ممنوع؛ Backoff/Jitter إلزامي |

## 7. ما يجب قياسه بعد كل اختبار فعلي

لوحة `teacher_delivery_health` تعرض:
- Retry events.
- Offline events.
- Request failures.
- Recovered events.
- Submit receipts.
- Pending attempts.

ومن Supabase Logs:
- HTTP status distribution.
- p50/p95/p99.
- 5xx/520 count.
- Edge region.
- execution time.

## 8. تفسير “قبل وبعد”

**قبل:** الحفظ الآلي موجود، لكن النسخة الدائمة للإجابات وIdempotent legacy finish لم يكونا مكتملي الحماية.

**بعد — مثبت وظيفيًا:** Local Draft + Retry + Finish Intent + Idempotency + Receipt + Recovery Grace + Telemetry.

**بعد — أداء إنتاجي طويل المدى:** لا يُعلن كرقم نهائي إلا بعد جمع نافذة تشغيل متجانسة بعد نشر الواجهة الجديدة. العينة الأولية لـ v105 جيدة، لكنها لا تكفي وحدها لإعلان SLA.
